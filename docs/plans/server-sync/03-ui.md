# Phase 3 — UI: settings, linking, status

Goal: a user can enable sync, link a second device, see sync status, and turn
it all off — without touching a dev console.

Depends on phase 2.

Scope note: this phase builds the shared shell (section layout, status
states, indicator, first-sync UX) plus the `server` provider's forms. The
`google-drive` provider adds its sign-in flow and provider chooser on top in
doc 05 Task 5.6 — design the section so a second provider slots in (the
disabled state renders per-provider connect affordances from the registry,
not a hardcoded form).

## Task 3.1 — Settings section "Sync"

New `frontend/src/pages/settings/sync.tsx` (+ `sync.module.css`), rendered from
`settings.tsx` using the existing `section.tsx` wrapper — model the layout on
`backup-restore.tsx`, which is the closest existing section (action buttons +
explanatory copy).

States the section renders:

1. **Disabled** — short explanation of what syncs (decks, campaigns, folders —
   not settings) and that the password cannot be reset (no email on file), with
   two explicit, separate flows sharing one username/password form:
   - "Create sync account" → password + confirm-password fields →
     `createSyncAccount(username, password)`. A 409 renders "username already
     taken". Include a "credentials are also your recovery — anyone with them
     has full access, so a play group can share one account" note.
   - "Sign in to existing account" → username + password →
     `linkSyncAccount(username, password)`. A 401 renders "unknown username
     or wrong password" — never fall through to creating an account, so a
     typo can't silently spawn an empty one (the backend's create/login split
     guarantees this, see phase 1 Task 1.3).
   Both buttons show a busy state: credential derivation alone takes a few
   hundred ms (Task 2.0) before any network call.
2. **Enabled** — username, last synced time, entity counts (from
   `GET /v2/sync/account`), buttons:
   - "Sync now" → `runSyncCycle()`
   - Linking another device needs no UI affordance at all: sign in with the
     same username/password there. Say exactly that in the section copy.
   - "Disable on this device" (keeps server data) and
     "Disable & delete server data" (calls `DELETE /v2/sync/account`) — the
     destructive one behind a confirmation dialog (reuse the app's existing
     confirm pattern from deck deletion).
3. **Error/offline** — surface `sync.lastError` inline.

Repo rules that apply here:

- Every string is an i18n key under `settings.sync.*` in
  `frontend/src/locales/en.json`; add the same keys to `de.json` (German UI
  localization exists — mark strings for translation review like the
  `docs/translations-de-review.md` flow if uncertain).
- No inline styles; CSS module per component.

## Task 3.2 — Global sync status indicator

Small passive indicator (icon + tooltip) showing `sync.status` /
`lastSyncedAt`, placed wherever the app's chrome makes sense (likely the
sidebar footer near the settings link — confirm against the actual layout in
`frontend/src/components/` when implementing). Clicking navigates to the
settings section. Only rendered when `sync.enabled`.

Keep it status-only; all actions live in settings.

## Task 3.3 — First-sync UX

`createSyncAccount`/`linkSyncAccount` from Task 3.1 run the phase-2 first-sync
merge, which can take a few seconds with a large collection:

- progress state on the button (`syncing…`), disable double-submits
- on completion, a toast/summary line: n decks, n campaigns synced,
  n conflicted copies created (if any)
- on failure (bad credentials, username taken, offline), inline error and no
  partial `enabled` state — create/link must be atomic from the UI's
  perspective.

## Task 3.4 — Backup/restore interaction (explicit direction)

A restore while sync is enabled must never be silently re-resolved by LWW
(the restored data is *older* than the remote replica, so a normal cycle
would revert it). The engine provides forced-direction modes (phase 2
Task 2.7); this task is the UI that makes the direction an explicit,
informed choice:

- **Restore dialog** (extends `backup-restore.tsx`): when sync is enabled,
  restoring shows a comparison before anything is applied —
  local: last change + deck/campaign counts; remote: last synced time +
  counts (from `accountInfo()`); backup file: its newest `date_update` +
  counts. The user then picks one of:
  - "Restore and overwrite synced data" → apply backup locally, then
    `forcePushLocal()` — every linked device converges on the backup.
  - "Restore on this device only" → apply backup locally and **disable
    sync on this device** (remote and other devices untouched).
  - Cancel.
- **Recovery actions** in the settings sync section, for the same either-
  direction control outside of restores: "Push local copy to remote" and
  "Replace local copy with remote", each behind a confirm dialog showing
  the same local-vs-remote times/counts so the user can see which side is
  newer before overriding. These are the escape hatches when sync state
  looks wrong.

All timestamps rendered with the app's existing date formatting; strings
under `settings.sync.*` / `backup.*` in `en.json` + `de.json`.
